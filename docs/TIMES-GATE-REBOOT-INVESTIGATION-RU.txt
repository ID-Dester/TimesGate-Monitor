TGm / DIVOOM TIMES GATE
ОТЧЁТ ПО РАССЛЕДОВАНИЮ ПЕРИОДИЧЕСКИХ ПЕРЕЗАГРУЗОК

Дата: 20.09.2026
Версия, передаваемая вместе с отчётом: TGm 0.1.0-preview.1-rc10

Этот документ предназначен для независимого анализа другим разработчиком.
TGm — неофициальное Windows-приложение для вывода показателей ПК на пять LCD
Divoom Times Gate. Проект не связан с Divoom и не одобрен Divoom.

Точная первопричина перезагрузки пока НЕ доказана. Ниже подтверждённые факты
отделены от гипотез.


1. КРАТКОЕ ОПИСАНИЕ ПРОБЛЕМЫ
============================

При длительной работе пяти LCD в режиме Divoom Network Text устройство иногда:

- начинает показывать повреждённые или смещённые строки;
- показывает сообщение вида "err at jsondecode!";
- прекращает запросы к локальному HTTP-серверу TGm сразу со всех LCD либо только
  с одного LCD;
- возвращается к стандартному циферблату Divoom;
- после общего события некоторое время недоступно по HTTP, затем снова начинает
  работать и может принять конфигурацию TGm.

Несколько восьмичасовых тестов прошли полностью успешно. Другие длительные тесты
завершались общим или выборочным отказом. Значит, проблема не возникает при
каждом запуске и не является простым немедленным конфликтом.

Внешнее измерение питания и внутренний uptime устройства пока отсутствуют.
Поэтому термин "перезагрузка" означает наблюдаемое поведение, похожее на reboot
устройства или restart его UI/network-процесса. Полный аппаратный power cycle
пока не доказан.


2. ТЕКУЩАЯ АРХИТЕКТУРА
======================

1. TGm получает CPU/GPU/RAM/system-метрики в Windows.
2. Встроенный локальный HTTP-сервер слушает LAN-адрес ПК, обычно порт 8765.
3. На каждый LCD один раз передаётся фоновое изображение.
4. Изменяемые значения реализованы полями Divoom Network Text. Times Gate сам
   обращается к HTTP endpoint TGm и получает короткий JSON.
5. Каждая строка является отдельным Network Text field. Прошивка некорректно
   отображала переносы строк внутри одного поля.
6. Номинальные интервалы:
   - CPU/GPU load: 5 секунд;
   - температуры, power и RAM: 10 секунд;
   - system-поля: 15 секунд;
   - служебный heartbeat LCD: 30 секунд.
7. Пользователь может установить минимальный интервал 5–30 секунд.
8. Конфигурация пяти LCD выполняется последовательно.

Первоначальная архитектура повторно генерировала и загружала картинку при каждом
изменении цифр. Часы почти постоянно показывали Loading, зависали и
перезагружались чаще. Переход к статическому фону плюс Network Text резко улучшил
стабильность, но не устранил редкие долгосрочные сбои.


3. РАЗНЫЕ ТИПЫ СОБЫТИЙ
======================

A. Общий вероятный reboot
-------------------------

Все пять LCD почти одновременно прекращают HTTP-запросы. Иногда Times Gate
временно перестаёт отвечать на health check по LAN. Затем появляются штатные
часы Divoom, запросы возобновляются и TGm повторно применяет пять экранов.

B. Отказ одного LCD
-------------------

Четыре экрана продолжают получать данные, один возвращается к штатному экрану
или перестаёт обращаться к TGm. Такой LCD восстанавливается отдельно.

C. Частичный Apply
------------------

Команды LCD1–LCD4 проходят, а LCD5 завершается тайм-аутом. До RC9 TGm очищал
сохранённое состояние до начала полного Apply. Неуспешный LCD5 после этого
ошибочно считался ненастроенным и исключался из heartbeat-контроля. RC9 сохраняет
последнее известное состояние до успешного Apply и устраняет этот дефект.

D. Отказ Windows CPU sensor host
--------------------------------

Это отдельная проблема и не причина reboot Times Gate. Повышенный reader
LibreHardwareMonitor/PawnIO может зависнуть. RC10 добавляет автоматический запуск
задания sensor host после трёх неудачных IPC-запросов и продолжает попытки с
интервалом 15 секунд.

5. ЧТО УЖЕ СДЕЛАНО
==================

5.1. Убрана постоянная загрузка изображений
-------------------------------------------

Фон загружается при конфигурации, цифры обновляются Network Text. Это устранило
постоянный Loading и заметно увеличило длительность стабильной работы.

5.2. Снижена частота обновления
------------------------------

Поля разделены на интервалы 5/10/15 секунд. Добавлен ползунок 5–30 секунд.
Наблюдалось, что при более частом обновлении проблема могла проявляться раньше,
но строгий контролируемый эксперимент ещё не проведён.

5.3. Изменено формирование HTTP-ответа
-------------------------------------

- ответы короткие и локальные;
- JSON отдаётся с фиксированным Content-Length;
- chunked transfer encoding для этих ответов не используется;
- строки разделены на независимые поля;
- команды пяти экранов отправляются последовательно.

5.4. Добавлена диагностика каждого LCD
--------------------------------------

- отдельный heartbeat endpoint;
- request/value counters;
- время последнего запроса;
- heartbeat journal каждые пять минут;
- estimated interruption/detected/recovered timestamps;
- 90 секунд тишины до признания экрана пропавшим;
- различение общего сбоя пяти LCD и отказа одного LCD.

5.5. Добавлено автоматическое восстановление
-------------------------------------------

- общий сбой: health check и повторный Apply пяти экранов;
- выборочный сбой: Apply одного LCD;
- backoff и cooldown между попытками;
- watchdog фоновой задачи контроля соединения;
- с RC9 неуспешный Apply не удаляет экран из наблюдения.

Ожидаемое восстановление после общего события занимает около 1,5–2 минут:
до 90 секунд подтверждения тишины, интервал проверки и последовательный Apply.

5.6. Проверена профилактика по числу запросов
--------------------------------------------

RC8 полностью переустанавливал пять экранов после 30 000 запросов. Эксперимент
оказался неудачным:

- успешный Apply не предотвратил последующий общий сбой;
- вторая профилактика сама оборвалась на LCD5;
- процедура добавляла команды и временно нарушала рабочий dashboard.

В RC9 и RC10 эта профилактика полностью удалена. TGm реагирует только на
фактически обнаруженный сбой.

5.7. Проверена базовая сеть
---------------------------

- Times Gate доступен по LAN на TCP 80;
- часы получают значения с локального порта TGm;
- VPN оставался включён, локальная подсеть добавлена в исключения;
- Kill Switch выключен;
- LAN IP ПК определяется автоматически.

Потеря маршрута может объяснить отсутствие данных, но хуже объясняет повреждённый
текст, jsondecode error и поведение, похожее на перезапуск.

5.8. Fan Control
----------------

Fan Control не выключался во время разработки и нескольких успешных
восьмичасовых тестов. Постоянный прямой конфликт не подтверждён. Он может влиять
на Windows sensor stack, но это не объясняет reboot самих часов.


6. РАБОЧИЕ ГИПОТЕЗЫ
====================

6.1. Утечка памяти или ресурса в Network Text firmware
------------------------------------------------------

Наиболее сильная текущая гипотеза. Пять LCD создают несколько длительных потоков
HTTP/JSON-запросов. После большого количества запросов могли накапливаться heap
objects, parser state, sockets, timers, widget objects или string cache.

Аргументы: зависимость от длительности/числа запросов, jsondecode error,
повреждённые строки, восстановление после reboot и отсутствие эффекта от
обычного повторного Apply.

6.2. Firmware JSON parser получает неполный ответ
-------------------------------------------------

Причиной может быть TCP reset, обрыв соединения, неверная обработка keep-alive
или внутренняя ошибка клиента Times Gate. Даже корректный Content-Length не
гарантирует, что прошивка всегда дочитает body.

6.3. Socket/connection exhaustion
---------------------------------

Возможна утечка keep-alive connections или неправильное повторное использование
сокетов. Следует сравнить текущий режим и принудительный Connection: close,
одновременно записывая число TCP-соединений.

6.4. Слишком высокая суммарная частота
--------------------------------------

Каждый interval может быть допустим отдельно, но сумма запросов пяти LCD и
нескольких fields может превышать расчётную нагрузку firmware.

6.5. Утечка именно при повторной конфигурации widgets
-----------------------------------------------------

Новый Apply может создавать внутренние объекты, не освобождая старые. Это
объясняет бесполезность или вред профилактики. Нужны сравнимые тесты с Apply и
без Apply при одинаковом числе value requests.

6.6. Wi-Fi/LAN/VPN
------------------

Сетевой джиттер или смена маршрута могут дать прерванный body. Гипотеза не
исключена без PCAP, ping и TCP-monitoring, но сама по себе плохо объясняет все
визуальные признаки.

6.7. Питание, перегрев или аппаратный дефект
--------------------------------------------

Не исключены блок питания, USB-кабель, перегрев и дефект экземпляра. Нет данных
о напряжении, потреблении, температуре устройства и аппаратном uptime.

6.8. Ошибка TGm HTTP runtime
----------------------------

Сервер продолжал отвечать другим LCD при выборочных сбоях, поэтому общее падение
Kestrel маловероятно. Редкий некорректный/прерванный ответ конкретному запросу
всё ещё возможен.


7. ОСЛАБЛЕННЫЕ ИЛИ ОПРОВЕРГНУТЫЕ ПРЕДПОЛОЖЕНИЯ
==============================================

1. "Fan Control всегда конфликтует с TGm" — ослаблено успешными восьмичасовыми
   тестами с постоянно работающим Fan Control.
2. "Повторный Apply до 35 000 запросов предотвратит reboot" — опровергнуто RC8.
3. "Причина только в загрузке изображений" — изображения были сильной отдельной
   нагрузкой, но редкие сбои остались после перехода на Network Text.
4. "Причина только в неверном IP/VPN" — ослаблено многочасовыми успешными LAN
   запросами, хотя краткий сетевой сбой исключить нельзя.


8. РЕКОМЕНДУЕМЫЕ ЭКСПЕРИМЕНТЫ
==============================

8.1. Кольцевая трассировка HTTP
-------------------------------

Для каждого запроса писать: UTC, LCD/field, connection id, remote endpoint,
HTTP version, Content-Length, безопасный хеш body, completed/aborted, duration,
число активных запросов и соединений. Нужен кольцевой файл последних нескольких
минут, чтобы не создавать гигантский лог.

8.2. Одновременный PCAP
----------------------

Проверить побайтовое совпадение body и Content-Length, TCP reset/retransmission,
момент закрытия соединения, рост количества sockets и пакеты перед jsondecode.

8.3. Матрица длительных тестов
------------------------------

A. Один LCD, interval 5 секунд.
B. Пять LCD, interval 30 секунд.
C. Пять LCD, interval 10 секунд.
D. Пять LCD, interval 5 секунд.
E. Пять LCD, одно постоянное Network Text field на экран.
F. Пять LCD с heartbeat и без heartbeat.

Для каждого теста фиксировать wall time и суммарное requests-to-failure. Если
число запросов повторяется лучше времени, это поддержит накопительную гипотезу.

8.4. Статический endpoint
-------------------------

Отдавать постоянный минимальный JSON без датчиков и изменения текста. Если reboot
останется при похожем числе запросов, можно исключить sensor collection и
форматирование значений.

8.5. Connection: close против keep-alive
----------------------------------------

Сравнить длительность работы в двух режимах при одинаковой частоте запросов.

8.6. Определить реальный тип reboot
----------------------------------

Снять видео, наблюдать загрузочную анимацию/LED, параллельно опрашивать ping и
TCP 80, измерять USB-питание, получить uptime через API при наличии. Это отделит
полный power reboot от restart UI/network service или сброса конфигурации LCD.

8.7. Firmware и документация Divoom
-----------------------------------

Зафиксировать firmware version, проверить обновления, запросить ограничения
Network Text: число fields, допустимые intervals, JSON schema/size и правила
HTTP connections. Рассмотреть альтернативный локальный протокол, если существует.


9. ПОВЕДЕНИЕ RC10
=================

RC10 не утверждает, что устраняет внутренний reboot Times Gate. Он должен
безопасно пережить событие:

- восстановить пять LCD после общей тишины;
- восстановить один LCD после выборочного отказа;
- не забыть экран после частичного Apply;
- не выполнять профилактический Apply по 30 000 запросов;
- сохранить heartbeat counters и временную шкалу в диагностике;
- автоматически вернуть отдельный Windows CPU sensor host после его зависания.

11. ДАННЫЕ, НУЖНЫЕ ПРИ СЛЕДУЮЩЕМ СБОЕ
=====================================

1. Точное местное время первого дефекта.
2. Фото/видео всех пяти LCD и возможной загрузочной анимации.
3. Диагностический ZIP сразу после восстановления.
4. Выбранный interval.
5. Состояние VPN/LAN/Wi-Fi.
6. Firmware version.
7. PCAP и расширенный HTTP trace после их реализации.

Не передавать публично LocalToken, VPN-конфигурации и ключи. Штатный экспорт TGm
исключает LocalToken и маскирует IP/пользовательские пути.


ИТОГ
====

Наиболее сильная гипотеза — накопительная ошибка памяти, Network Text widgets,
JSON parser или HTTP connection state внутри firmware Times Gate. Повторная
конфигурация не сбрасывает это состояние. Для доказательства необходимы PCAP,
побайтовая серверная трассировка и контролируемая матрица тестов по количеству
LCD, fields и интервалам.
